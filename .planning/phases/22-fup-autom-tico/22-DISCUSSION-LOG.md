## Area 1: Canal de saída do FUP

**Q: Como o scheduler FUP entrega a mensagem ao lead?**
- Options: FUP_WEBHOOK_URL ENV / EventPublisher com action='fup' / FUP_REPLY_QUEUE ENV (RabbitMQ)
- **Decision:** FUP_WEBHOOK_URL ENV
- Rationale: Transporte de saída independente; operador aponta para Z-API/Twilio. EventPublisher é para telemetria — canais diferentes.

**Q: O FUP_WEBHOOK_URL deve ser obrigatório ou silencioso se ausente?**
- Options: FUP desativado sem FUP_WEBHOOK_URL (sem erro) / Erro no startup se fup_config existir
- **Decision:** FUP desativado sem FUP_WEBHOOK_URL (sem erro)
- Rationale: Mesmo padrão do EventPublisher — Brain funciona sem FUP ativo se ENV ausente.

## Area 2: Localização do Scheduler

**Q: Onde o scheduler FUP roda?**
- Options: Dentro do BrainRunner (setInterval), inicializado em init() e parado em close() / Módulo standalone em apps/brain-*
- **Decision:** Dentro do BrainRunner (setInterval)
- Rationale: Sem infra adicional; ciclo de vida compartilhado com BrainRunner; mesmo padrão de mcpClient e eventPublisher.

**Q: SQL próprio ou reutiliza o sql do BrainRunner?**
- Options: Reutiliza o sql do BrainRunner / SQL próprio via nova conexão
- **Decision:** Reutiliza o sql do BrainRunner
- Rationale: TenantPoolManager já gerencia pool; nova conexão seria desperdício.

**Q: Concorrência entre instâncias: como garantir FUP único?**
- Options: SELECT FOR UPDATE SKIP LOCKED em leads (FUP-02) / Advisory lock por lead (pg_advisory_lock)
- **Decision:** SELECT FOR UPDATE SKIP LOCKED em leads (FUP-02)
- Rationale: REQUIREMENTS.md especifica exatamente este padrão. Advisory lock é mais complexo sem benefício.

## Area 3: Prompt e conteúdo do FUP

**Q: De onde vem o texto do FUP?**
- Options: Tabela prompts com key='fup' / Hardcoded default por brain_type / ENV FUP_PROMPT_TEMPLATE
- **Decision:** Tabela prompts com key='fup'
- Rationale: Zero alterações de schema; consistente com key='system', key='qualifier'; operacionalizável via INSERT.

**Q: O scheduler inclui histórico da conversa na geração LLM?**
- Options: Sim — via PostgresSaver.getTuple(thread_id) / Não — apenas prompt + dados do lead
- **Decision:** Sim — via PostgresSaver.getTuple(thread_id)
- Rationale: FUP-03 especifica histórico contextualizado. Mensagem genérica sem contexto teria menor conversão.

**Q: O que acontece se não existir prompt 'fup' no banco?**
- Options: FUP é pulado (warn + skip) — sem prompt = sem FUP / Usa prompt hardcoded de fallback / Erro visível no log
- **Decision:** FUP é pulado (warn + skip)
- Rationale: Fail-safe; operador deve inserir o prompt antes de ativar FUP. Não crashar por config ausente.

**Q: O FupScheduler deve publicar EVT-03 (evento de FUP) ao enviar com sucesso?**
- Options: Sim — implementar EVT-03 aqui (reutiliza IEventPublisher da Phase 20) / Não — deixar para fase futura
- **Decision:** Sim — implementar EVT-03 aqui
- Rationale: EVT-03 estava mapeado na Phase 20 mas não foi implementado. Phase 22 fecha esse gap usando a infraestrutura já pronta.

**Q: Estrutura do campo result no evento FUP?**
- Options: `{ step: number, message: string }` — estruturado / `string` — texto simples / `{ step, message, leadId, timestamp }` — verbose

- Rationale: Estruturado e mínimo — identifica o step atual e o conteúdo enviado sem duplicar dados do envelope.
