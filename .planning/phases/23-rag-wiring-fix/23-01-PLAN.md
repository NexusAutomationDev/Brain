<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM → search_knowledge tool | O LLM controla `query` e `collections[]` — inputs não sanitizados chegam à tool antes de ir ao pgvector |
| search_knowledge → pgvector | A query vetorial (embedding gerado pela tool) é passada ao banco; não há SQL dinâmico gerado por input do usuário |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-01 | Tampering | `search_knowledge` `collections[]` input | mitigate | Zod schema já tem `z.array(z.string().min(1)).min(1)` — rejeita arrays vazios e strings vazias; validação ocorre na definição da tool via LangChain `tool()` |
| T-23-02 | Information Disclosure | pgvector similarity search | accept | Brain SDR só acessa o banco do próprio tenant via `ctx.sql` injetado — isolamento de tenant já garantido pela arquitetura multi-tenant existente; sem cross-tenant access path |
| T-23-03 | Elevation of Privilege | LLM escolhendo collections arbitrárias | accept | Collections são nomes de string sem efeito de permissão; search retorna resultados vazios para collections inexistentes — sem impacto de segurança; INGEST_TOKEN controla o que entra, não o que sai via search |
| T-23-04 | Denial of Service | LLM chamando search_knowledge em loop | accept | handleToolErrors: true no ToolNode captura erros; context window limita histórico a 40 mensagens; sem mecanismo de rate-limit interno nesta fase — aceito para v1.4 scope |
</threat_model>
