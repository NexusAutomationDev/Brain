Close the remaining Phase 28 (Embedding SDK) code-review findings: unbounded `reembed.ts` pagination (WR-03), a stale/misleading `EMBEDDING_DIMENSIONS=768` comment in `ingest.ts` (WR-01), unescaped/untruncated chunk content in `search-knowledge.ts`'s LLM-facing output (IN-02), and no cross-check that `EMBEDDING_DIMENSIONS` matches Gemini's fixed 3072-dimension output (IN-03).

Purpose: `reembed.ts`'s per-row-UPDATE pagination loop has no upper bound — a knowledge base that grows large enough (or a `collection` filter that unexpectedly matches most of the table) turns a single `POST /api/v1/reembed` call into an unbounded, potentially runaway job with no operator-visible ceiling. `search-knowledge.ts` formats raw DB `content` directly into the LLM-facing tool response with no length cap — a future ingestion path or manual DB edit that produces an oversized chunk could blow up context budget or leak formatting artifacts. The Gemini dimension mismatch is currently a silent footgun: `GeminiEmbeddingProvider` always outputs 3072-dim vectors regardless of what `EMBEDDING_DIMENSIONS` says, so a misconfigured ENV value doesn't fail until the first embed call hits the `vector(N)` column and gets a cryptic Postgres dimension error.
Output: `reembed.ts` capped at a bounded number of pages; `search-knowledge.ts` truncates oversized chunk content; `gemini-provider.ts` fails fast on `EMBEDDING_DIMENSIONS != 3072`; `ingest.ts`'s comment corrected to match the real default.
</objective>

    // output. Chunks from the standard ingest path (chunker.ts CHUNK_SIZE=1000) never hit
