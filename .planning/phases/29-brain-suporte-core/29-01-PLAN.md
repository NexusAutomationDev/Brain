<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Webhook ingress (`POST /api/v1/webhook`) | Untrusted external payload (WhatsApp/CRM) crosses into `WebhookTransport` → `BrainRunner.run()`. Same boundary already hardened for brain-sdr (`WEBHOOK_TOKEN` bearer auth), inherited unchanged by `createWebhookApp(runner)`. |
| RabbitMQ ingress | Untrusted message body from queue crosses into `RabbitMQTransport` consumer → `BrainRunner.run()`. Same DLQ/retry handling inherited unchanged from `@brain-pkg/transport`. |
| LLM tool-calling boundary | LLM output (`tool_calls`) is semi-trusted — `routeAfterLlm` inspects `tool_calls[0].name` to route; a malformed/injected tool name that doesn't match `"respond"` falls through to `"tools"` node, where `ToolNode` only executes tools present in `filteredAllTools` (closed set). |
| `thread_id` boundary | `config.configurable.thread_id` is set exclusively by `BrainRunner` from `lead.uniqueId` (never from LLM output or request body) before reaching `pause_session`/`finish_conversation` — this is the existing SDR mitigation, unchanged. |
| `BRAIN_TOOLS` env / `enabledTools` filter boundary | Operator-controlled ENV, not user-controlled — trusted input, but D-04 introduces a deliberate exception (search_knowledge bypasses this filter) that must not be exploitable as a way to leak unintended tools. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-01 | Tampering | `buildGraph()` D-04 bypass logic (`filteredAllTools = [...filteredExceptSearch, boundSearchKnowledgeTool]`) | mitigate | `boundSearchKnowledgeTool` is a fixed, closure-bound reference created inside `buildGraph()` — it is appended by direct variable reference, not by name lookup against user/LLM input, so there is no way for an attacker to substitute a different tool via this code path. Task 1 acceptance criteria greps for the exact `filteredExceptSearch` / `boundSearchKnowledgeTool` pattern to prevent regression to a name-based (spoofable) bypass. |
| T-29-02 | Elevation of Privilege | LLM tool_calls routing (`routeAfterLlm`) | accept | Inherited unchanged from brain-sdr, already in production. `ToolNode` only ever executes tools present in the closed `filteredAllTools` array — LLM cannot invoke arbitrary function names, only what's bound. Risk already accepted at SDR launch; no new surface introduced by Suporte. |
| T-29-03 | Information Disclosure | `DATABASE_PASSWORD` / `MCP_AUTH_TOKEN` / `WEBHOOK_TOKEN` in logs | mitigate | `index.ts` ENV validation log explicitly omits `DATABASE_PASSWORD` value (only logs which var names are missing) — same pattern copied verbatim from brain-sdr (T-09-03-05). No new logging statements introduced in this plan touch secret values. |
| T-29-04 | Denial of Service | `search_knowledge` always bound regardless of `BRAIN_TOOLS` | accept | Structural requirement (SUP-02) — RAG cannot be disabled by design. Query-level cost controls (topK=5, cosine threshold=0.5) are already hardcoded in `createSearchKnowledgeTool` (packages/core, unchanged) and apply identically to Suporte. No additional DoS surface vs. SDR's existing search_knowledge usage. |
| T-29-05 | Repudiation | Tool execution on `leads` table (`pause_session`, `finish_conversation`) without audit trail beyond `updatedAt` | accept | Same posture as brain-sdr (production-accepted) — `IEventPublisher` fire-and-forget event log (`packages/core/src/runner/runner.ts` TOOL_EVENTS_WHITELIST) already covers `pause_session`/`finish_conversation`/`qualify_lead`; Suporte inherits this whitelist unchanged (whitelist already includes `pause_session`/`finish_conversation` — no code change needed in this plan). |
