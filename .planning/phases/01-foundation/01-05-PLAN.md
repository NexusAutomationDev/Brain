<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → GET /health | Qualquer cliente pode chamar o endpoint — sem autenticação em Phase 1 |
| performHealthCheck → PostgreSQL | O health check executa `SELECT 1` no banco — requer conexão TCP |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Information Disclosure | GET /health response | mitigate | O endpoint expõe apenas `status`, `checks.db`, `version` (commit hash ou "unknown"), e `timestamp` — NUNCA incluir DATABASE_URL, credenciais, stack traces, ou nomes de tabelas na resposta. A função `performHealthCheck` já foi implementada com essa restrição em health.ts. |
| T-05-02 | Denial of Service | GET /health endpoint | accept | O endpoint é de health check (baixo valor para ataque); o `SELECT 1` é fast-path (<1ms); sem auth significa que qualquer cliente pode chamar, mas o custo por request é mínimo. Em Phase 1 (desenvolvimento), sem rate limiting é aceitável. |
| T-05-03 | Spoofing | Sql instance injetada em performHealthCheck | accept | Em Phase 1, o `Sql` é construído pelo TenantPoolManager com credenciais do env — sem input externo no path de criação do pool usado pelo health check. |
| T-05-04 | Tampering | Hono app routing | accept | Somente GET /health está exposto; não há rotas de escrita; Hono não expõe filesystem nem permite path traversal em rota estática. |
</threat_model>

**Passo 2: Criar `packages/observability/src/server.ts` com o conteúdo abaixo.**

O server deve:
- Exportar `createHealthApp(sql: Sql): Hono` — cria o app Hono com a rota GET /health injetando a instância `Sql`
- Exportar `startServer(sql: Sql, port?: number): void` — inicializa o servidor Bun com o app
- Aplicar os HTTP status codes de D-14: 200 para ok, 503 para checks.db === 'failed', 500 para status === 'error'
- Usar `createLogger` para logar a porta ao iniciar o servidor (consistente com OBS-01)
- NUNCA incluir DATABASE_URL ou credenciais na resposta (T-05-01)

```typescript
import { Hono } from 'hono';
import type { Sql } from 'postgres';
import { createLogger } from './logger.js';
import { performHealthCheck } from './health.js';

/**
 * Creates a Hono application with the GET /health route.
 *
 * OBS-02: Exposes health check endpoint per D-13 and D-14.
 * The sql instance is injected so the caller controls which DB connection is checked.
 *
 * @param sql - postgres.js Sql instance to use for DB connectivity check
 */
export function createHealthApp(sql: Sql): Hono {
  const app = new Hono();

  app.get('/health', async (c) => {
    const result = await performHealthCheck(sql);

    // D-14: HTTP status codes
    // 200 = ok, 503 = dependency (DB) failed, 500 = internal error
    const httpStatus =
      result.status === 'ok'
        ? 200
        : result.checks.db === 'failed'
          ? 503
          : 500;

    return c.json(result, httpStatus);
  });

  return app;
}

/**
 * Starts the HTTP server using Bun.serve.
 *
 * @param sql - postgres.js Sql instance for health check
 * @param port - Port to listen on (default: PORT env or 3000)
 */
export function startServer(sql: Sql, port?: number): void {
  const app = createHealthApp(sql);
  const listenPort = port ?? parseInt(process.env.PORT || '3000', 10);
  const logger = createLogger({ service: 'health-server' });

  Bun.serve({
    port: listenPort,
    fetch: app.fetch,
  });

  logger.info({ port: listenPort }, 'Health server listening');
}
```

**Nota sobre o Sql injetado:** O consumidor de `startServer` ou `createHealthApp` é responsável por fornecer a instância `Sql`. Em testes, pode-se passar um mock. Em runtime, o consumidor usaria `TenantPoolManager.getPool(databaseName)` ou uma instância direta de `postgres(DATABASE_URL)`.

Criar `packages/observability/src/server.test.ts` com testes reais (não todo) que verificam o comportamento do endpoint GET /health.

Os testes devem usar `mock.module` para interceptar `performHealthCheck` diretamente — essa é a abordagem primária, pois evita o problema de semântica de tagged template functions com mocks simples (a `Sql` do postgres.js usa template literals como `sql\`SELECT 1\``, e um mock de função normal não satisfaz essa interface corretamente no caso de falha).

```typescript
import { describe, it, expect, mock, beforeEach } from 'bun:test';

// Mock do módulo health.ts ANTES de importar server.ts
// Isso intercepta performHealthCheck sem depender da semântica de tagged template da Sql
let mockShouldSucceed = true;

mock.module('./health.js', () => ({
  checkDatabase: mock(async () => mockShouldSucceed),
  performHealthCheck: mock(async (_sql: unknown) => {
    if (mockShouldSucceed) {
      return {
        status: 'ok' as const,
        checks: { db: 'connected' as const },
        version: 'test',
        timestamp: new Date().toISOString(),
      };
    }
    return {
      status: 'error' as const,
      checks: { db: 'failed' as const },
      version: 'test',
      timestamp: new Date().toISOString(),
    };
  }),
}));

// Importar server APÓS configurar o mock
import { createHealthApp } from './server.js';
import type { Sql } from 'postgres';

// Sql mock mínimo — createHealthApp injeta mas performHealthCheck está mockado acima
const fakeSql = {} as unknown as Sql;

describe('GET /health (OBS-02)', () => {
  beforeEach(() => {
    mockShouldSucceed = true;
  });

  describe('when database is connected', () => {
    it('returns HTTP 200', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      expect(res.status).toBe(200);
    });

    it('returns JSON with status "ok"', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      const body = await res.json();
      expect(body.status).toBe('ok');
    });

    it('returns checks.db: "connected"', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      const body = await res.json();
      expect(body.checks.db).toBe('connected');
    });

    it('returns timestamp as ISO string', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      const body = await res.json();
      expect(typeof body.timestamp).toBe('string');
      expect(() => new Date(body.timestamp)).not.toThrow();
    });
  });

  describe('when database is unreachable', () => {
    beforeEach(() => {
      mockShouldSucceed = false;
    });

    it('returns HTTP 503', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      expect(res.status).toBe(503);
    });

    it('returns checks.db: "failed"', async () => {
      const app = createHealthApp(fakeSql);
      const req = new Request('http://localhost/health');
      const res = await app.fetch(req);
      const body = await res.json();
      expect(body.checks.db).toBe('failed');
    });
  });
});
```

**Por que `mock.module` em vez de mock de tagged template:** A função `checkDatabase` em `health.ts` usa `sql\`SELECT 1\`` — tagged template literal. Um `mock(async () => ...)` simples retorna uma função normal, não uma tagged template function, então `sql\`SELECT 1\`` lançaria `TypeError: sql is not a function` ou retornaria valor incorreto no caso `shouldSucceed: false`. Usar `mock.module('./health.js', ...)` intercepta `performHealthCheck` inteiramente, eliminando a dependência da semântica de `Sql`.
