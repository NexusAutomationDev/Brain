<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM-controlled `query` string → `embeddingProvider.embedQuery()` → external API | The search query text originates from LLM tool-call arguments (ultimately user-influenced conversation content) and is sent to OpenAI/Gemini's embedding API |
| `knowledge_chunks.embedding_model` filter → search results | Determines which vectors are compared — an incorrect/missing filter would silently produce meaningless similarity scores (D-14/D-17) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-06 | Information Disclosure | Failure-path of `ingest.ts`'s embedding call (Pitfall 3 guard) | mitigate | The new empty-vector guard (Task 1) logs only `{ collection, totalChunks/failed/succeeded counts }` — never the chunk content or the API error's raw response body, matching the existing `logger.info`/`logger.warn` discipline already in `ingest.ts`. |
| T-28-07 | Tampering (silent data corruption) | `search.ts`'s `embeddingModel` filter — cross-provider vector mixing | mitigate | D-17: the existing `eq(knowledgeChunks.embeddingModel, embeddingModel)` filter in `search.ts` is preserved unchanged and now sourced directly from `IEmbeddingProvider.providerName` (Task 1) rather than a separately-resolved `resolveEmbeddingModel()` call — removes a possible drift point where the filter value and the actual embedding provider used at query-time could diverge if `EMBEDDING_MODEL`/`LLM_PROVIDER` env vars changed between the two calls. |
</threat_model>
