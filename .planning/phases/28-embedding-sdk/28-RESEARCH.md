## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Extract `packages/ai/src/embeddings/factory.ts` into a new `packages/embeddings` package (the package `ROADMAP.md`/`REQUIREMENTS.md` already specify).
- **D-02:** `IEmbeddingProvider` **replaces** `createEmbeddings()` in all existing callers — `packages/core/src/tools/search-knowledge.ts` and `packages/core/src/rag/ingest.ts` receive an injected `IEmbeddingProvider` instead of calling the `packages/ai` factory directly. No two coexisting embedding paths.
- **D-03:** Keep Gemini support alongside OpenAI — `GeminiEmbeddingProvider` alongside `OpenAIEmbeddingProvider`, preserving what already works today (`GoogleGenerativeAIEmbeddings` in the current factory). REQUIREMENTS.md only requires OpenAI (EMBD-02) as the minimum, but removing Gemini would be a regression.
- **D-04:** `OpenAIEmbeddingProvider` and `GeminiEmbeddingProvider` wrap the LangChain wrappers (`OpenAIEmbeddings`, `GoogleGenerativeAIEmbeddings`) — same pattern used by `createLLM()` in `packages/ai/src/llm/factory.ts` (returns the LangChain type, does not call the official SDK directly).
- **D-05:** Confirmed: no real production clients yet — only dev/test environments. The fix can be direct, without a real-data migration plan.
- **D-06:** Create a **new migration `0009`** with `ALTER COLUMN TYPE vector(N)` — do not edit the already-applied migration `0007` (keeps Drizzle's history immutable).
- **D-07:** Migration `0009` is generated via `drizzle-kit generate` with `EMBEDDING_DIMENSIONS` set in `.env` **at generation time** — the SQL is static/literal (Drizzle's standard pattern), no runtime interpolation. Changing the dimension again in the future requires generating another migration. This is expected/correct behavior, to be documented for operators.
- **D-08:** Wire up **both** integration points identified in `packages/core/src/runner/runner.ts`: embed the user's message before `getContext()` (line ~296, today `queryVector` empty) **and** embed `profileValue` in `saveContext()` (lines ~377-385, today no `embedding` field — this is the original MEM-03).
- **D-09:** Embedding the user's message is **blocking**, part of the main flow — `getContext()` depends on the generated vector to do semantic search; it cannot be fire-and-forget like `IEventPublisher`.
- **D-10:** Graceful fallback on embedding call failure — log the error and continue with empty `queryVector` / without saving the embedding. Never break lead service because of this. Same resilience pattern already used in the project (MCP fallback, `IEventPublisher` fire-and-forget).
- **D-11:** Introduce `EMBEDDING_PROVIDER` as a dedicated ENV **in this phase** (not wait for Phase 29) — already documented as aspirational in `CLAUDE.md`.
- **D-12:** When `EMBEDDING_PROVIDER` is absent, auto-resolve to a provider **capable of generating embeddings** — formalizing behavior that already exists in `resolveEmbeddingModel()`: `LLM_PROVIDER=gemini` → embedding via Gemini; any other value (including `anthropic`, which has no embedding API) → default to OpenAI. **Not** a literal mirror of `LLM_PROVIDER` — a conscious capability mapping.
- **D-13:** Direct consequence of D-12: changing `LLM_PROVIDER` (e.g. openai → anthropic) does **not** automatically affect embedding — RAG stays stable unless `EMBEDDING_PROVIDER`/`EMBEDDING_MODEL` is explicitly changed.
- **D-14:** **Confirmed via research** (see Specific Ideas): vectors generated by different providers/models (e.g. Gemini vs OpenAI) are **not comparable to each other**, even with the same numeric dimension — this is a real limitation of the embedding models, not an implementation gap. No conversion/adapter exists that makes this compatible.
- **D-15:** `BrainRunner.init()` validates whether `IEmbeddingProvider.dimensions` matches the dimension expected by the DB's `vector(N)` column and fails fast with a clear message **before** accepting messages — avoids an obscure Postgres error mid-conversation with a real lead.
- **D-16:** Phase 28 includes a basic batch re-embed tool — endpoint/script that reprocesses embeddings of existing `knowledge_chunks` using the currently configured provider/model, **without re-uploading/re-ingesting original documents** (each chunk's text is already preserved in the table).
- **D-17 (consequence of D-14):** `search_knowledge` must avoid mixing vectors from incompatible `embedding_model`s in the same search — otherwise similarity results become silently meaningless. Exact mechanism (strict filter by current `embedding_model` vs. other criteria) is Claude's Discretion.
- **Explicitly limited scope of the re-embed tool:** not the enterprise-grade zero-downtime pipeline (shadow index + similarity threshold recalibration + event-driven architecture) described in research — it is a basic batch reprocessing tool. The full industry-grade pattern is recorded in Deferred Ideas.

### Claude's Discretion

- Exact name/path of the re-embed endpoint/script (e.g. `POST /api/v1/reindex` vs standalone CLI script).
- Exact filter mechanism by `embedding_model` in `search_knowledge` (strict exclusion vs. warning + inclusion).
- Internal structure of `packages/embeddings` (file names, exports) — as long as `IEmbeddingProvider`, `OpenAIEmbeddingProvider`, and `GeminiEmbeddingProvider` are exported.

### Deferred Ideas (OUT OF SCOPE)

- **Enterprise-grade zero-downtime pipeline for model switching** (shadow index + similarity threshold recalibration + event-driven architecture, per the Drift-Adapter paper pattern) — Phase 28 only delivers a basic batch re-embed tool (D-16). Since each Brain runs on its own per-client DB, in practice this is not a blocker now — but noted for Phase 29 reassessment if needed.

## Summary

This phase formalizes embedding infrastructure that already works in production-adjacent code (`packages/ai/src/embeddings/factory.ts`, used by RAG ingest/search) into a proper `packages/embeddings` package with an `IEmbeddingProvider` interface. The core technical work is mechanical extraction + two specific gap fixes (hardcoded `vector(1536)`, dead semantic-write path) + one new capability (batch re-embed tool).

Two verified findings materially affect planning. First, empirical testing against a live `pgvector/pgvector:pg16` container confirms `ALTER COLUMN TYPE vector(N)` **succeeds cleanly with no `USING` clause on an empty table** (matches D-05's "no real prod data" premise) — but **fails hard** (`ERROR: expected N dimensions, not M`) if any row has a different dimension, and `USING NULL` as a workaround also fails on a `NOT NULL` column. Since `packages/database` migrations run automatically via `runMigrations()` with an advisory lock on every `BrainRunner.init()`, plan the 0009 migration knowing dev/test databases must be empty (or truncated) of `embeddings`/`knowledge_chunks` rows before it applies, or it will fail at startup.

Second — and this is new information not surfaced during the discuss-phase session — the installed `@langchain/google-genai@2.1.31` (and even the latest stable `2.2.0`) `GoogleGenerativeAIEmbeddings` class has **no `dimensions`/`outputDimensionality` parameter at all** in its constructor or `embedQuery`/`embedDocuments` methods (confirmed by reading the installed `.d.ts` and `.cjs` source). Additionally, Google deprecated the `text-embedding-004` model on January 14, 2026 — it is already failing with "model not found" errors in production. The current `DEFAULT_MODELS.gemini = "text-embedding-004"` in the factory is broken today, independent of this phase's other work. This must be fixed as part of `GeminiEmbeddingProvider` (model bump to `gemini-embedding-001`, which defaults to 3072 dimensions, not 768) or explicitly flagged for user confirmation, since it also affects `EMBEDDING_DIMENSIONS` compatibility with existing OpenAI-generated vectors (D-14's exact scenario).

**Primary recommendation:** Port `createEmbeddings()`'s logic almost verbatim into two provider classes (`OpenAIEmbeddingProvider`, `GeminiEmbeddingProvider`) implementing `IEmbeddingProvider`, wire `BrainRunner` via the exact `IEventPublisher` optional-injection pattern already proven in `runner.ts`, generate migration `0009` against an empty/truncated test DB, and treat the Gemini model deprecation as a must-fix bundled into D-03's "preserve what already works" — because what "already works" for Gemini is currently broken upstream.

### Pattern 1: IEmbeddingProvider interface reconciling REQUIREMENTS.md with LangChain's dual-method surface

**What:** REQUIREMENTS.md (EMBD-01) specifies a single `embed(texts): Promise<number[][]>` method, but the existing production code and the LangChain `Embeddings` base class both use two distinct methods: `embedQuery(text: string): Promise<number[]>` (single string, query-time) and `embedDocuments(texts: string[]): Promise<number[][]>` (batch, ingest-time). These are NOT interchangeable in the codebase today — `search-knowledge.ts` calls `embedQuery`, `ingest.ts` calls `embedDocuments`.

**When to use:** Always for this phase — this is the interface every provider and every caller depends on.

**Example (recommended shape, reconciling both needs):**
```typescript
// packages/embeddings/src/provider.interface.ts
// Source: reconciles REQUIREMENTS.md EMBD-01 with existing LangChain call sites
// (packages/core/src/tools/search-knowledge.ts uses embedQuery,
//  packages/core/src/rag/ingest.ts uses embedDocuments)
export interface IEmbeddingProvider {
  /** Batch embedding for documents/chunks (ingest-time). Matches EMBD-01's embed() intent. */
  embed(texts: string[]): Promise<number[][]>;
  /** Single-text embedding for queries (search-time). Needed because query-time embedding
   *  is semantically distinct (some providers use taskType=RETRIEVAL_QUERY vs RETRIEVAL_DOCUMENT). */
  embedQuery(text: string): Promise<number[]>;
  readonly dimensions: number;
  readonly providerName: string;
}
```
See Open Questions Q1 for the discretion point on whether `embed()` is the sole required method (per literal REQUIREMENTS.md text) with `embedQuery` as a convenience, or whether both are first-class.

### Pattern 2: EMBEDDING_PROVIDER capability-aware resolution (D-11/D-12/D-13)

**What:** Formalize the existing inline `resolveEmbeddingModel()` capability mapping into an explicit factory keyed on a new `EMBEDDING_PROVIDER` ENV, independent from `LLM_PROVIDER`.

**When to use:** `packages/embeddings/src/factory.ts`, single entry point called by `BrainRunner.init()`.

**Example:**
```typescript
// packages/embeddings/src/factory.ts
// Source: formalizes packages/ai/src/embeddings/factory.ts resolveEmbeddingModel() (D-12)
import { ConfigurationError } from "@brain-pkg/shared";
import type { IEmbeddingProvider } from "./provider.interface.js";

const CAPABLE_PROVIDERS = new Set(["openai", "openrouter", "gemini"]);

/**
 * D-12: EMBEDDING_PROVIDER is independent from LLM_PROVIDER.
 * When absent, falls back to a provider CAPABLE of generating embeddings —
 * anthropic (no embedding API) always falls back to openai.
 */
function resolveEmbeddingProviderName(): string {
  const explicit = process.env.EMBEDDING_PROVIDER?.trim();
  if (explicit) return explicit;
  const llmProvider = process.env.LLM_PROVIDER?.trim();
  if (llmProvider && CAPABLE_PROVIDERS.has(llmProvider)) return llmProvider;
  return "openai"; // D-12: default for anthropic or unset LLM_PROVIDER
}

export async function createEmbeddingProvider(): Promise<IEmbeddingProvider> {
  const provider = resolveEmbeddingProviderName();
  switch (provider) {
    case "gemini": {
      const { GeminiEmbeddingProvider } = await import("./gemini-provider.js");
      return new GeminiEmbeddingProvider();
    }
    case "openai":
    case "openrouter":
      const { OpenAIEmbeddingProvider } = await import("./openai-provider.js");
      return new OpenAIEmbeddingProvider();
    default:
      throw new ConfigurationError(`Unknown EMBEDDING_PROVIDER: ${provider}`, { provider });
  }
}
```

### Pattern 3: BrainRunner DI — mirrors the proven IEventPublisher pattern exactly

**What:** `IEmbeddingProvider` is injected the same way `IEventPublisher` already is: optional constructor param in `BrainRunnerOptions`, resolved from ENV inside `init()` if not injected, tested by passing a fake implementation directly (no `mock.module`).

**Verified in `packages/core/src/runner/runner.ts` (read directly, lines 41-54, 79, 95-106, 154-163):**

  // ...
  eventPublisher?: IEventPublisher;   // ← mirror this exact shape for embeddingProvider?: IEmbeddingProvider

  // ...
  if (options.eventPublisher) {
    this.eventPublisher = options.eventPublisher;

### Pattern 4: Dimension fail-fast check (D-15) via `pg_attribute.atttypmod`

**What:** Query the live `vector(N)` column's declared dimension directly from Postgres system catalogs and compare to `IEmbeddingProvider.dimensions` at `BrainRunner.init()` time, before accepting messages.

**Empirically verified** against a live `pgvector/pgvector:pg16` container — `atttypmod` for the `vector` type returns the raw dimension with **no typmod offset** (unlike `varchar`, which stores `N+4`):

```sql
-- VERIFIED via direct psql query against pgvector/pgvector:pg16 container:
-- CREATE TABLE t (embedding vector(768) not null);
-- SELECT atttypmod FROM pg_attribute WHERE attrelid='t'::regclass AND attname='embedding';
--   → returns exactly 768 (not 772, not encoded)
SELECT atttypmod AS dimensions
FROM pg_attribute
WHERE attrelid = 'knowledge_chunks'::regclass
  AND attname = 'embedding'
  AND attnum > 0;
```

```typescript
// packages/core/src/runner/runner.ts — inside init(), after runMigrations() and embeddingProvider resolution
const [{ dimensions: columnDim }] = await this.sql<{ dimensions: number }[]>`
  SELECT atttypmod AS dimensions
  FROM pg_attribute
  WHERE attrelid = 'knowledge_chunks'::regclass
    AND attname = 'embedding'
    AND attnum > 0
`;
if (columnDim !== this.embeddingProvider.dimensions) {
  this.logger.error(
    { expected: columnDim, actual: this.embeddingProvider.dimensions, providerName: this.embeddingProvider.providerName },
    "EMBEDDING_DIMENSIONS mismatch — provider dimensions do not match the vector(N) column. Fix EMBEDDING_DIMENSIONS or regenerate migration."
  );
  process.exit(1); // D-15: fail-fast before accepting messages — matches existing process.exit(1) pattern in init()
}
```

Alternative equivalent query using `format_type()` (also verified working, more human-readable but requires string parsing — `atttypmod` is preferred for programmatic comparison):
```sql
SELECT format_type(atttypid, atttypmod) FROM pg_attribute WHERE attrelid='knowledge_chunks'::regclass AND attname='embedding';
-- → returns the string 'vector(768)' — verified empirically
```

### Anti-Patterns to Avoid

- **Calling `createEmbeddingProvider()` more than once per BrainRunner lifecycle:** resolve once in `init()`, store as instance field — same pattern as `checkpointer`/`memoryManager`. Recreating per-`run()` call wastes a dynamic import and, for OpenAI, re-validates API key unnecessarily.
- **Trusting `GoogleGenerativeAIEmbeddings.embedDocuments()` to throw on partial batch failure:** it does not (see Pitfall 3) — always check for empty-array sentinels in the result before writing to `knowledge_chunks`.
- **Assuming `EMBEDDING_DIMENSIONS` changes take effect without a new migration:** per D-07, this is fully expected/correct behavior, not a bug — but the re-embed tool and `BrainRunner.init()` fail-fast check exist specifically because operators WILL forget this.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Retrying failed OpenAI/Gemini embedding requests | Custom retry loop | LangChain's built-in `caller` (`this.caller.call(...)`) already wraps both `OpenAIEmbeddings` and `GoogleGenerativeAIEmbeddings` methods with retry logic | Confirmed by reading installed source — `GoogleGenerativeAIEmbeddings.embedQuery`/`embedDocuments` already route through `this.caller.call()` `[VERIFIED: installed embeddings.cjs]` |
| Batching large document sets for OpenAI | Custom chunking loop before calling the API | `OpenAIEmbeddings.embedDocuments()` already internally batches via `chunkArray(texts, this.batchSize)` (default `batchSize=512`, OpenAI API max 2048) | Confirmed in installed source `[VERIFIED: installed embeddings.cjs]` — hand-rolling this duplicates existing, correct behavior |
| Vector dimension introspection tooling | Custom migration-state tracking table | `pg_attribute.atttypmod` system catalog query (Pattern 4) | Postgres already stores this; no additional bookkeeping table needed |
| Embedding-model versioning/compatibility tracking | New schema/table for "which model produced which vector" | `knowledge_chunks.embedding_model` column — already exists (RAG-04), already used by `search.ts`'s `eq(knowledgeChunks.embeddingModel, embeddingModel)` filter | Re-verified in `search.ts` D-03a — this is the exact mechanism D-17 should extend, not replace |

**Key insight:** Nearly all of Phase 28's "hard parts" (retry, batching, model-compatibility tracking) are already solved by existing dependencies or existing schema — the actual net-new work is the interface extraction, the ENV wiring, and the migration.

## Runtime State Inventory

> Included because EMBD-03 involves a schema/migration change and EMBD-05 changes a currently-dead code path to active — both carry runtime-state risk even though this isn't a rename phase.

| Category | Items Found | Action Required |

## Common Pitfalls

### Pitfall 1: `ALTER COLUMN TYPE vector(N)` fails hard on non-empty tables — no implicit truncation or padding

**What goes wrong:** Running migration 0009 against a database that already has rows in `embeddings` or `knowledge_chunks` (e.g. a dev DB seeded during earlier phases' testing) throws `ERROR: expected N dimensions, not M` and the entire migration transaction rolls back — `BrainRunner.init()` then calls `process.exit(1)` per the existing `runMigrations()` catch block in `runner.ts`.

**Why it happens:** Postgres's `ALTER COLUMN TYPE` for `vector` requires all existing values to already match the new dimension exactly; there is no implicit cast, padding, or truncation for vector types (confirmed empirically — this is not documented explicitly in pgvector's README).

**How to avoid:** Migration 0009's SQL should include an explicit `TRUNCATE` (or `DELETE FROM`) of `embeddings` and `knowledge_chunks` immediately before the `ALTER COLUMN TYPE` statements, OR the plan should mandate that dev/test DBs are truncated as a prerequisite/manual step before applying. Given D-05 confirms no real prod data exists, including the `TRUNCATE` directly in the migration SQL is the safer, self-contained choice — it makes the migration idempotent and safe to run against any dev/test DB state without a separate manual step.

**Warning signs:** `BrainRunner` fails to start with a Postgres error containing `"expected N dimensions, not M"` in the logs; `runMigrations()`'s catch block logs `"Migrations failed — aborting init"`.

**Verified:** Empirically tested against `pgvector/pgvector:pg16` — confirmed both the failure mode and that an empty table (or `TRUNCATE`d table) allows a clean, instant `ALTER COLUMN TYPE` with no `USING` clause, and that an existing HNSW index on the column survives the type change without needing to be dropped/recreated manually. `[VERIFIED: direct psql testing against pgvector/pgvector:pg16]`

### Pitfall 2: Gemini's default embedding model is deprecated and already failing

**What goes wrong:** The current `DEFAULT_MODELS.gemini = "text-embedding-004"` in `packages/ai/src/embeddings/factory.ts` (to be ported into `GeminiEmbeddingProvider`) points to a model Google deprecated on January 14, 2026. Calls to this model are already returning "model not found" errors as of research date (2026-06-30).

**Why it happens:** This predates Phase 28 — it is pre-existing tech debt in the current `factory.ts` that nobody noticed because Gemini is not the default provider path (`openai` is the default per `resolveEmbeddingModel()`) and may not be actively exercised in current testing/usage.

**How to avoid:** When porting to `GeminiEmbeddingProvider`, update the default model to `gemini-embedding-001`. **Critical downstream consequence:** `gemini-embedding-001`'s default output is 3072 dimensions (vs. `text-embedding-004`'s 768) — this changes what `EMBEDDING_DIMENSIONS` value is expected for Gemini-configured Brains, and per Pitfall 3 below, **cannot be reduced via any parameter exposed by the installed LangChain wrapper**. This is a decision point that needs explicit user confirmation (flagged in Assumptions Log) since it affects D-14's exact "switch providers" scenario and may require `EMBEDDING_DIMENSIONS=3072` for any Gemini-configured Brain, which is incompatible with OpenAI's 1536/768/etc. defaults on the same column dimension unless explicitly configured to match.

**Warning signs:** Any test or manual verification of the Gemini embedding path returns an error mentioning "text-embedding-004", "not found", or "not supported for embedContent".

**Verified:** `[VERIFIED: WebSearch cross-referenced against Google's own deprecation notices and multiple independent community reports (n8n, genkit, LangChain docs) — high-confidence, multi-source corroboration]`

### Pitfall 3: `GoogleGenerativeAIEmbeddings.embedDocuments()` silently swallows per-batch failures

**What goes wrong:** Reading the installed source directly (`_embedDocumentsContent`): batches are sent via `Promise.allSettled(...)`, and any batch that fails (`status !== "fulfilled"`) is replaced with `Array(batchLength).fill([])` — i.e., **empty arrays, not thrown errors**. A caller that doesn't explicitly check for empty-array results will silently write empty/invalid embeddings to `knowledge_chunks` for an entire failed batch (`maxBatchSize = 100` documents per Gemini batch).

**Why it happens:** This is intentional LangChain design for partial-failure resilience across batches, but it means "embedding succeeded" (promise resolved) does not mean "embedding is valid" — callers must inspect the actual vector arrays.

**How to avoid:** In `ingest.ts` and the new batch re-embed tool, after calling `embed()`/`embedDocuments()`, explicitly check `vectors.some(v => v.length === 0)` before inserting into `knowledge_chunks`, and fail/retry/log those specific rows rather than trusting a resolved promise. This matters most for the batch re-embed tool (D-16), which is likely to process larger volumes and hit Gemini's smaller `maxBatchSize=100` more often than OpenAI's `batchSize=512`.

**Warning signs:** `knowledge_chunks.embedding` rows with an empty/zero-length vector array (would break `cosineDistance` calls in `search.ts` at query time with unclear errors).

**Verified:** `[VERIFIED: installed @langchain/google-genai@2.1.31 source, embeddings.cjs, _embedDocumentsContent method — read directly, not inferred]`

### Pitfall 4: `@langchain/google-genai` has no way to control output dimensionality at all in the installed/latest version

**What goes wrong:** Unlike `OpenAIEmbeddings` (which exposes a `dimensions?: number` constructor param, confirmed working against `text-embedding-3` models), `GoogleGenerativeAIEmbeddings`'s constructor and `embedQuery`/`embedDocuments` methods have **zero exposed way** to pass Google's native `outputDimensionality` API parameter — confirmed by reading the full constructor and `_convertToContent()`/`_embedQueryContent()`/`_embedDocumentsContent()` source, none of which reference `outputDimensionality`. This gap exists in the installed `2.1.31` AND the latest stable `2.2.0` — there is an open LangChain forum feature request for this, unresolved as of research date.

**Why it happens:** The LangChain JS integration for Google GenAI embeddings has not been updated to expose this Google API feature (the Python LangChain integration reportedly supports it via method-level kwargs, but the JS package does not).

**How to avoid:** `EMBEDDING_DIMENSIONS` for Gemini-configured Brains is effectively locked to whatever `gemini-embedding-001` returns natively (3072) — there is no way to request a smaller dimension through this LangChain wrapper today. If a Brain needs Gemini AND a specific dimension smaller than 3072, the only paths are: (a) accept 3072 as the column dimension for that Brain's DB, or (b) bypass the LangChain wrapper entirely and call the raw `@google/genai` SDK inside `GeminiEmbeddingProvider` instead of `GoogleGenerativeAIEmbeddings` (a bigger scope change, likely out of scope for this phase — flag for user decision).

**Warning signs:** N/A at runtime (no error) — this is a silent capability gap, not a crash. Worth surfacing during planning/discuss so the user isn't surprised later.

**Verified:** `[VERIFIED: installed embeddings.d.ts + embeddings.cjs for both 2.1.31 (installed) and 2.2.0 (latest, downloaded and inspected directly)]`

### Pitfall 5: `drizzle-kit generate` requires a real TTY for interactive rename-detection prompts

**What goes wrong:** Running `drizzle-kit generate` non-interactively (piped stdin, CI, or certain sandboxed shells) can hit `Error: Interactive prompts require a TTY terminal` if drizzle-kit's snapshot diff perceives any ambiguity between created/deleted table or column entries (its `tablesResolver`/`columnsResolver` rename-detection heuristic).

**Why it happens:** Drizzle-kit's diffing algorithm always invokes a resolver step that only actually renders an interactive prompt when it finds items in both "missing" and "created" sets for the same entity type — this can be triggered by unrelated snapshot-state drift, not just genuine ambiguity in the schema change being made.

**How to avoid:** Generate migration 0009 from a real interactive terminal (not a piped/non-TTY automation context), and verify the migrations folder's `meta/_journal.json`/snapshot files are in sync with the actually-applied migration history before running `generate`. If automation is required, investigate `drizzle-kit generate --name <name>` behavior with a properly synced snapshot state first — this pitfall was observed during this research's verification attempt in a scratch environment with a deliberately out-of-sync test DB, so it may not reproduce with a correctly-initialized dev DB; flagged as LOW confidence risk requiring direct verification with a properly migrated dev DB during execution, not blocking for planning.

**Warning signs:** `drizzle-kit generate` exits with a TTY error instead of producing a `.sql` file.

**Confidence:** LOW — `[ASSUMED: reproduced once in a scratch test environment with unverified snapshot-sync state; root cause not conclusively isolated to the vector-dimension change itself]`. See Assumptions Log A1.

### OpenAIEmbeddingProvider — direct, verified port of existing factory logic

```typescript
// packages/embeddings/src/openai-provider.ts
// Source: ports packages/ai/src/embeddings/factory.ts (OpenAI branch), verified against
// installed @langchain/openai@1.4.7 embeddings.d.ts constructor signature
import type { OpenAIEmbeddings } from "@langchain/openai";
import type { IEmbeddingProvider } from "./provider.interface.js";

export class OpenAIEmbeddingProvider implements IEmbeddingProvider {
  readonly providerName = "openai";
  readonly dimensions: number;
  private embedder: OpenAIEmbeddings | null = null;
  private readonly model: string;
  private readonly apiKey?: string;

  constructor(options?: { model?: string; dimensions?: number; apiKey?: string }) {
    this.model = options?.model ?? process.env.EMBEDDING_MODEL ?? "text-embedding-3-small";
    this.dimensions = options?.dimensions ?? parseInt(process.env.EMBEDDING_DIMENSIONS ?? "1536", 10);
    this.apiKey = options?.apiKey ?? process.env.API_KEY;
  }

  private async getEmbedder(): Promise<OpenAIEmbeddings> {
    if (!this.embedder) {
      const { OpenAIEmbeddings } = await import("@langchain/openai");
      // VERIFIED: dimensions param confirmed in installed .d.ts constructor signature
      this.embedder = new OpenAIEmbeddings({
        model: this.model,
        openAIApiKey: this.apiKey,
        dimensions: this.dimensions,
      });
    }
    return this.embedder;
  }

  async embed(texts: string[]): Promise<number[][]> {
    const embedder = await this.getEmbedder();
    return embedder.embedDocuments(texts); // internally batches at 512 (verified in source)
  }

  async embedQuery(text: string): Promise<number[]> {
    const embedder = await this.getEmbedder();
    return embedder.embedQuery(text);
  }
}
```

### Batch re-embed tool skeleton — pagination + partial-failure awareness (D-16)

```typescript
// Sketch for the batch re-embed tool — exact endpoint/script shape is Claude's Discretion.
// Source: reconciles knowledgeChunks schema (packages/database/src/schema/tables.ts) with
// OpenAI rate limits (verified: text-embedding-3-small = 3000 RPM / 1M TPM on Tier 1) and
// Gemini's silent-failure batching behavior (Pitfall 3).
import { knowledgeChunks } from "@brain-pkg/database";
import { eq, and, ne } from "drizzle-orm";

const PAGE_SIZE = 200; // conservative — stays well under both providers' batch limits

async function reembedCollection(db, provider: IEmbeddingProvider, collection: string) {
  let offset = 0;
  for (;;) {
    const rows = await db
      .select()
      .from(knowledgeChunks)
      .where(and(eq(knowledgeChunks.collection, collection), ne(knowledgeChunks.embeddingModel, provider.providerName)))
      .limit(PAGE_SIZE)
      .offset(offset);
    if (rows.length === 0) break;

    const vectors = await provider.embed(rows.map((r) => r.content));

    for (let i = 0; i < rows.length; i++) {
      if (vectors[i].length === 0) {
        // Pitfall 3: skip and log — do not write an empty vector
        continue;
      }
      await db.update(knowledgeChunks)
        .set({ embedding: vectors[i], embeddingModel: provider.providerName, updatedAt: new Date() })
        .where(eq(knowledgeChunks.id, rows[i].id));
    }
    offset += PAGE_SIZE;
  }
}
```

## Open Questions

1. **Does `IEmbeddingProvider.embed()` fully replace `embedQuery()`, or do both coexist?**
   - What we know: REQUIREMENTS.md's EMBD-01 literally specifies `embed(texts): Promise<number[][]>` as the sole interface method. But `search-knowledge.ts` today calls `.embedQuery(query)` (singular, string in/vector out) — a different signature.
   - What's unclear: Whether `embed([query])[0]` is an acceptable substitution for `embedQuery(query)` at the call site (functionally equivalent for OpenAI; for Gemini, `taskType` semantics differ between document vs. query embedding, though the current code doesn't set `taskType` at all so this may be moot in practice).
   - Recommendation: Include both `embed()` and `embedQuery()` in the interface (Pattern 1) since it's a strict superset of REQUIREMENTS.md's literal ask and avoids `embed([text])[0]` ceremony at every query-time call site — but flag this as a discretion point for the planner/user since it technically extends beyond EMBD-01's literal text.

2. **Should `GeminiEmbeddingProvider` bypass the LangChain wrapper entirely to get `outputDimensionality` support?**
   - What we know: The installed and latest `@langchain/google-genai` wrapper has no dimension control at all (Pitfall 4). The raw Google `@google/genai` SDK does support `config: { outputDimensionality: N }` directly.
   - What's unclear: Whether this phase should invest in a non-LangChain-wrapped Gemini provider (bigger deviation from D-04's "mirror createLLM() pattern" decision) or accept the 3072-dimension-only limitation for Gemini.
   - Recommendation: Default to accepting the limitation (matches D-04's locked decision to use LangChain wrappers) and document `EMBEDDING_DIMENSIONS` must equal 3072 when `EMBEDDING_PROVIDER=gemini` with the default model — surfaced as Assumption A2 for user confirmation.
