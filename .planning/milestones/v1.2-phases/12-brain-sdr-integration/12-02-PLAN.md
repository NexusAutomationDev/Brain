## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP caller → handler.ts | Caller envia BrainEvent; handler valida antes de processar |
| handler.ts → caller (response) | Response inclui fullResponse (conteúdo do LLM) — opaco; caller é responsável por sanitização |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-02-01 | Information Disclosure | handler.ts — fullResponse no body da resposta | accept | fullResponse é opaco para o handler; é string gerada pelo LLM e repassada diretamente. Sanitização é responsabilidade do downstream (WhatsApp/CRM). Handler nunca loga fullResponse. |
| T-12-02-02 | Tampering | Remoção do campo reply (D-02 — breaking change) | accept | Decisão de design consciente — sem backward-compat shim. Downstream que consomem reply precisam migrar para fullResponse. |
| T-12-02-03 | Spoofing | Autenticação webhook via WEBHOOK_TOKEN | mitigate | Guard existente em handler.ts (T-vcu-01/T-vcu-03): fail-closed quando WEBHOOK_TOKEN ausente (503), Bearer token verificado em todas as requests (401 se inválido). Não muda nesta fase. |
| T-12-02-04 | Tampering | Input validation via BrainEventSchema | mitigate | `BrainEventSchema.safeParse(body)` existente em handler.ts retorna 400 para payloads inválidos. Não muda nesta fase — validação mantida. |
</threat_model>
