## Integration Findings (gsd-integration-checker)

### Gap Não-Fatal: brain-echo missing `hasOtherToolCall` guard

**Arquivo:** `apps/brain-echo/src/brain.ts:86-103`
**Afeta requisitos:** MCP-04 (interação com RESP-01 em brain-echo)

O nó LLM do brain-echo tem apenas 2 branches (`hasRespondCall` / `!hasRespondCall`). Quando o LLM chama uma MCP tool (não-respond), cai no branch `!hasRespondCall` e define `brainOutput: { fullResponse: "", responseMode: "undefined" }` como estado intermediário — antes de o loop ReAct continuar para a tool e retornar ao LLM.

O brain-sdr tem um guard explícito `hasOtherToolCall` (linhas 151-161) que pula a definição de `brainOutput` completamente quando uma tool não-respond é chamada.

**Por que não é fatal:** O reducer `last-write-wins` em `BrainStateAnnotation.brainOutput` garante que a escrita do nó `respond` (ao final do loop) sobrescreve o valor intermediário. O estado final após `invoke()` é correto.

**Edge case de falha:** Se o LLM terminar a execução sem chamar `respond` após receber o resultado de uma MCP tool, `brainOutput.fullResponse=""` falharia no `BrainOutputSchema.parse()` (campo `.min(1)`). Este path já é coberto pelo fallback PITFALL-6 no nó LLM, mas o intermediate state pollution adiciona ambiguidade.

**Ação recomendada:** Adicionar `hasOtherToolCall` guard em brain-echo alinhando com brain-sdr.
